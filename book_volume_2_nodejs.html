1. Introduction to Node.js: V8, Runtime & Core Architecture
📌 1.1 Definition & Purpose

Node.js is an open-source, cross-platform JavaScript runtime environment built on Google Chrome's V8 JavaScript Engine. It allows JavaScript to execute outside the browser directly on server operating systems (Linux, macOS, Windows). Instead of the traditional multi-threaded, blocking request-per-thread model (e.g., Apache/Java), Node.js uses an event-driven, non-blocking I/O model that makes it lightweight, highly scalable, and capable of handling tens of thousands of concurrent connections on minimal hardware.

🧠 1.2 Under the Hood: The 3 Core Pillars
  1. Google V8 Engine (C++): Compiles JavaScript directly into native machine code (Just-In-Time compilation). Manages the Call Stack and Memory Heap (Garbage Collector).
  2. Libuv (C Library): The beating heart of Node.js. Provides the cross-platform Event Loop, non-blocking asynchronous I/O abstractions (epoll on Linux, kqueue on macOS, IOCP on Windows), and a 4-thread worker pool for blocking operations.
  3. Node.js Core Bindings & C++ Addons: Low-level bridges (using Node-API/v8 APIs) connecting JS scripts to OS facilities (networking sockets, file system descriptors, cryptography, zlib compression).

Architecture Senior / 8-12 LPA

Q: If Node.js is single-threaded, how does it handle tens of thousands of concurrent I/O operations without freezing?

Key Answer: Node.js is single-threaded only at the JavaScript execution layer (the V8 Call Stack). The underlying I/O operations are offloaded to **Libuv**. Libuv utilizes non-blocking operating system kernel primitives (such as epoll on Linux, kqueue on macOS, and IOCP on Windows) which asynchronously monitor thousands of network sockets in hardware. For operations where OS kernel async support is unavailable (file system I/O, DNS resolution, and crypto hashing), Libuv offloads the work to an internal **Worker Thread Pool** (default 4 threads). When an operation finishes, its callback is queued in the Event Loop and pushed to the single main thread.
2. Libuv Internals: Single Thread, Kernel Epoll & Thread Pool
📌 2.1 Definition & Purpose

Libuv is a multi-platform C support library originally developed for Node.js. It abstracts asynchronous I/O across platforms and orchestrates the event-driven lifecycle. While network sockets are handled asynchronously by the OS kernel, certain blocking operations are offloaded to Libuv’s internal Worker Thread Pool.

🧠 2.2 What Actually Runs on the Libuv Thread Pool?

A common interview misconception is that all async operations run on the Libuv thread pool. In reality, ONLY 4 specific subsystems use the Libuv thread pool:

  1. File System Operations (fs.*): Almost all operating systems lack truly asynchronous file system APIs (unlike network sockets).
  2. DNS Lookups (dns.lookup()): Uses the blocking system POSIX getaddrinfo(). (Note: dns.resolve() bypasses the thread pool using c-ares!).
  3. Crypto Operations: CPU-heavy hashing such as crypto.pbkdf2(), crypto.scrypt(), and bcrypt hashing.
  4. Zlib Compression: Asynchronous compression algorithms (zlib.gzip()).
🔬 Bio-Anatomy: Kernel Async Socket vs Libuv Thread Pool File I/O LIBUV WORKFLOW
1. Incoming TCP Request ──> Handled by OS Kernel (epoll/kqueue) ──> Zero Libuv Threads used!
2. fs.readFile("data.csv") ──> Offloaded to Libuv Worker Thread #1
3. crypto.pbkdf2() ──> Offloaded to Libuv Worker Thread #2
4. bcrypt.hash() ──> Offloaded to Libuv Worker Thread #3
5. dns.lookup("google.com")──> Offloaded to Libuv Worker Thread #4
6. 5th blocking task arrives ──> QUEUED & BLOCKED until a thread becomes free!

Q: What is UV_THREADPOOL_SIZE, and how do you properly scale it in production?

Key Answer: UV_THREADPOOL_SIZE is an environment variable that sets the number of worker threads allocated by Libuv for file I/O, DNS lookups, and crypto tasks. The default is 4, and it can be scaled up to a maximum of 1024. It MUST be set in the shell environment before the Node process boots (e.g. UV_THREADPOOL_SIZE=16 node app.js). Setting process.env.UV_THREADPOOL_SIZE = 16 inside JS code often fails if any native module initializes before that line executes.
3. The Event Loop: The 6 Distinct Execution Phases
📌 3.1 Definition & Phase Cycle

The Node.js Event Loop runs continuously in a loop while the process is alive. One full cycle of the loop is known as a Tick. In each tick, the event loop traverses through 6 distinct phases in exact, strict sequential order.

💻 3.2 Practical Code Example: setTimeout vs setImmediate Race
timer_vs_immediate.jsNode.js Runnable
const fs = require("fs");

// Scenario A: In the main module (Non-deterministic output!)
// Depends on CPU performance and clock precision (0-1ms)

setImmediate(() => console.log("Main Immediate"));

// Scenario B: Inside an I/O callback (100% Deterministic!)
// After I/O Poll phase, Event Loop ALWAYS enters the Check phase first!

    setTimeout(() => console.log("I/O Timeout"), 0);
    setImmediate(() => console.log("I/O Immediate (Always Wins!)"));
});
💼 3.3 Sudheer J Style Interview Q&A Cards
Event Loop Senior / 10 LPA

Q: Why is setImmediate() guaranteed to execute before setTimeout(fn, 0) inside an I/O cycle?

Key Answer: In an I/O cycle, the callback is being processed inside the Poll phase of the event loop. Once the poll phase completes, the event loop naturally transitions forward to the Check phase, which directly executes setImmediate. The setTimeout callback was queued in the Timers phase, which cannot be reached until the current cycle finishes and loops back to Phase 1 in the next tick. Therefore, inside any I/O cycle, setImmediate will ALWAYS execute before setTimeout(fn, 0).
4. Async I/O: Blocking vs Non-Blocking Code Execution
📌 4.1 Definition & Impact on Throughput

Blocking refers to operations where execution of additional JavaScript on the Call Stack must pause until a non-JavaScript operation (such as disk I/O or network reads) completes. Non-blocking operations initiate the request and return immediately, allowing the Call Stack to continue serving concurrent HTTP users while the operating system handles the I/O in the background.

💻 4.2 Practical Code Example: The Catastrophic Sync File Read Bug
blocking_server_danger.jsNode.js Anti-Pattern
const http = require("http");
const fs = require("fs");

const server = http.createServer((req, res) => {
    if (req.url === "/bad") {
        // ⚠️ BLOCKING ANTI-PATTERN: Completely freezes the server thread for ALL users!
        const data = fs.readFileSync("/large_file.zip"); 
        res.end(data);
    } else {
        // ✅ NON-BLOCKING PATTERN: Event Loop remains free!
        fs.readFile("/large_file.zip", (err, data) => {
            if (err) res.statusCode = 500;
            res.end(data);
        });
    }
});
5. Modules: CommonJS (CJS) vs ES Modules (ESM) Interoperability
📌 5.1 Definition & Architecture

Node.js historically supported CommonJS (CJS) using require() and module.exports. Modern Node.js natively supports standard ES Modules (ESM) using import and export.

🔬 Bio-Anatomy: CommonJS Module Wrapper Function CJS INTERNALS
Before your CommonJS code is executed, Node.js wraps it in an IIFE:
(function(exports, require, module, __filename, __dirname) {
// YOUR CODE LIVES HERE
const db = require('./db');
module.exports = { ... };
});
This is why __filename and __dirname exist in CJS, but are UNDEFINED in ES Modules!

Q: Can you require() an ES Module inside a CommonJS file? What about the reverse?

Key Answer: Synchronously calling require('./esm-module.js') will throw ERR_REQUIRE_ESM because ES Modules are parsed asynchronously. 6. NPM Internals: package.json, package-lock.json & SemVer
📌 6.1 Definition & Purpose

NPM (Node Package Manager) is the default package registry and dependency management CLI for Node.js. It maintains the project's dependency tree, scripts, and runtime engine constraints.

🧠 6.2 package.json vs package-lock.json
  • package.json: High-level manifest declaring dependencies, devDependencies, and SemVer version ranges.
  • package-lock.json: Deterministic snapshot containing the exact resolved version, download URL, and cryptographic SHA-512 integrity hash of every nested package in the entire dependency tree. Eliminates "works on my machine" bugs.
⚡ 6.3 Semantic Versioning (SemVer) Rules: MAJOR.MINOR.PATCH

~ (Tilde)~4.18.2Accepts PATCH bugfixes only (>= 4.18.2 < 4.19.0).
Exact (No symbol)4.18.2Locks to that precise version only.

💼 6.4 Sudheer J Style Interview Q&A Cards
NPM Internals Senior / 7 LPA

Q: What is the exact difference between 'npm install' and 'npm ci'? Which one must be used in CI/CD production pipelines?

Key Answer: npm install can update package-lock.json if newer matching dependencies satisfy the ranges in package.json. In contrast, npm ci (Clean Install) is strictly deterministic: it deletes the existing node_modules folder, reads exclusively from package-lock.json, never modifies the lockfile, and throws a fatal error if package.json and package-lock.json are out of sync. Always use npm ci in automated CI/CD and Docker builds!

8. Path Module: path.join() vs path.resolve() & Directory Resolution
📌 8.1 Definition & Key Difference

The path module handles file and directory paths across different operating systems (handling Windows backslash \ vs POSIX forward slash / automatically).

  • path.join([...paths]): Concatenates all path segments together using the platform-specific delimiter and normalizes relative segments (.. and .).
  • path.resolve([...paths]): Resolves a sequence of paths into an absolute path, processing from right to left prepending the current working directory (process.cwd()) until an absolute root is formed.

9. JSON Storage: Serialization, Deserialization & Atomic File Writes
📌 9.1 Definition & Backend Pitfalls

In Node.js backends, JSON files often store local settings, seed data, and small databases. Direct concurrent writes to JSON files can cause file corruption if the server crashes mid-write.

💻 9.2 Practical Code: Atomic JSON Storage Pattern
atomic_json_storage.jsProduction Pattern
const fs = require("fs/promises");
const path = require("path");

async function atomicSaveJson(filePath, data) {
    const tempPath = `${filePath}.${Date.now()}.tmp`;
    const serialized = JSON.stringify(data, null, 2);

    // 1. Write to temporary file first
    await fs.writeFile(tempPath, serialized, "utf8");

    // 2. Atomic rename (OS-level atomic operation - zero corruption risk!)
    await fs.rename(tempPath, filePath);
    console.log("JSON data atomically saved to:", filePath);
}
10. Process: process.argv, process.env & Graceful Shutdown Hooks
📌 10.1 Definition & Purpose

The global process object provides control over the currently running Node.js process. In backend production deployments, it manages CLI flags, environment variables, and intercepts termination signals (SIGTERM, SIGINT) to execute Graceful Shutdowns (closing DB pools and active HTTP connections without dropping in-flight user requests).

💻 10.2 Production Backend Implementation: Graceful Shutdown
graceful_shutdown.jsProduction Pattern
const http = require("http");

const server = http.createServer((req, res) => {
    res.end("Server active!");
});

server.listen(3000, () => console.log("App listening on port 3000"));

// Graceful Shutdown Handler
function handleShutdown(signal) {
    console.log(`
Received ${signal}. Starting graceful shutdown...`);
    
    server.close(() => {
        console.log("HTTP server closed. Closing database connections...");
        // Close DB connections here (e.g. mongoose.connection.close())
        process.exit(0);
    });

    // Force shutdown after 10s timeout if hung
    setTimeout(() => {
        console.error("Forced shutdown: timeout reached!");
        process.exit(1);
    }, 10000);
}

process.on("SIGTERM", () => handleShutdown("SIGTERM")); // Sent by Kubernetes / Docker / Render
process.on("SIGINT", () => handleShutdown("SIGINT"));   // Ctrl+C from terminal

12. Buffers: Raw Binary Memory, Encodings & 8KB Slab Allocation
📌 12.1 Definition & Purpose

A Buffer is a fixed-size chunk of raw binary memory allocated outside the V8 JavaScript Heap directly by Node.js using C++ memory allocators. Buffers are essential for reading files, processing binary network packets, image resizing, and stream chunking.

🧠 12.2 Buffer.alloc() vs Buffer.allocUnsafe() & The 8KB Slab
  • Buffer.alloc(size): Allocates memory and zero-fills (clears) every byte. Safe, but slightly slower.
  • Buffer.allocUnsafe(size): Fast, but allocates raw uninitialized memory that may contain sensitive leaked data (passwords, tokens) previously in RAM! Always zero it out or fill it immediately.
  • 8KB Buffer Slab Pool: Node.js pre-allocates an 8KB memory slab (Buffer.poolSize = 8192) to quickly carve out small buffer slices without issuing repeated expensive OS system calls.
💻 12.3 Practical Code Example: Binary Data & Encoding Conversion

14. Backpressure: High-Volume Data Handling & The 'drain' Event
📌 14.1 Definition & Mechanism

Backpressure occurs when a fast data producer (e.g. reading from a fast SSD at 500 MB/s) sends data faster than a slow consumer can process or transmit it (e.g. writing to a slow 3G client at 50 KB/s). Without backpressure control, unconsumed chunks accumulate in RAM buffers until the server crashes with ERR_OUT_OF_MEMORY.

🧠 14.2 The write() and drain Mechanism
  1. When data is written to a writable stream via writable.write(chunk), it buffers data up to highWaterMark (default 16KB / 64KB).
  2. If the internal buffer fills up, writable.write(chunk) returns false.
  3. The producer MUST immediately pause reading (readable.pause()).
  4. Once the consumer empties its internal buffer, the writable stream emits the 'drain' event. The producer can then safely resume (readable.resume()).
💻 14.3 Practical Code Example: Writing 10 Million Rows with Backpressure Safety
backpressure_drain.jsNode.js Runnable
const fs = require("fs");

function writeHugeDataset(writer, totalRows, callback) {
    let i = totalRows;
    
    function write() {
        let ok = true;
        while (i > 0 && ok) {
            i--;
            const data = `Row #${i}: Data payload
`;
            if (i === 0) {
                // Final row
                writer.end(data);
            } else {
                // If write() returns false, STOP and wait for 'drain'!
                ok = writer.write(data);
            }
        }
        if (i > 0) {
            // Buffer full! Wait for drain event
            writer.once("drain", write);
        }
    }
    write();
}

const writeStream = fs.createWriteStream("huge_dataset.csv");
writeHugeDataset(writeStream, 1000000, () => console.log("Done!"));
15. Events: EventEmitter & Memory Leak Prevention
📌 15.1 Definition & Purpose

Much of Node.js core architecture is built around an idiomatic asynchronous event-driven architecture using the EventEmitter class (e.g. HTTP servers, streams, sockets). An EventEmitter exposes .on() to attach listeners and .emit() to broadcast named events with payloads.

⚠️ 15.2 The MaxListenersExceededWarning Leak Trap

By default, if more than 10 listeners are attached to a single event on an emitter, Node.js outputs: MaxListenersExceededWarning: Possible EventEmitter memory leak detected. This usually happens when an event listener is mistakenly added inside a per-request route handler!

💻 15.3 Practical Code Example: Custom Production EventEmitter
order_events.jsNode.js Runnable
const EventEmitter = require("events");

17. Worker Threads: Solving CPU-Intensive Tasks in Node.js
📌 17.1 Child Process vs Worker Threads
  • Child Process (child_process.fork): Creates a completely separate OS process with its own PID, separate memory space (~30MB base overhead), and communication via IPC serialization.
  • Worker Thread (worker_threads): Runs inside the same process on a separate OS thread with its own independent V8 engine and Event Loop, but can share memory directly via SharedArrayBuffer (almost zero memory overhead!).
💻 17.2 Practical Code Example: Offloading CPU Heavy Work
worker_thread_demo.jsNode.js Runnable
const { Worker, isMainThread, parentPort, workerData } = require("worker_threads");

if (isMainThread) {
    // Main Thread: Remains 100% responsive to incoming HTTP requests!
    const worker = new Worker(__filename, { workerData: { iterations: 1e8 } });
    
    worker.on("message", (result) => {
        console.log("Worker thread finished sum:", result);
    });
} else {
    // Worker Thread: Executes heavy CPU math without freezing the Main Thread
    let total = 0;
    for (let i = 0; i < workerData.iterations; i++) {
        total += i;
    }
    parentPort.postMessage(total);
}
18. Cluster Module: Multi-Core Hardware Scaling & PM2 Internals
📌 18.1 Definition & Purpose

A single Node.js instance runs on a single CPU core. On an 8-core or 16-core server, running a basic node app.js leaves 87.5% of hardware power idle. The cluster module spawns worker processes that all share the exact same server port (via OS socket passing / round-robin scheduling).

💻 18.2 Practical Code Example: Zero-Downtime Cluster Server
cluster_server.jsNode.js Runnable
const cluster = require("cluster");
const http = require("http");
const os = require("os");

if (cluster.isPrimary) {
    const numCPUs = os.cpus().length;
    console.log(`Primary process ${process.pid} is running. Forking ${numCPUs} workers...`);

    // Fork workers for each CPU core
    for (let i = 0; i < numCPUs; i++) {
        cluster.fork();
    }

    // Auto-respawn crashed workers (Self-healing system)
    cluster.on("exit", (worker, code, signal) => {
        console.log(`Worker ${worker.process.pid} died. Forking replacement worker...`);
        cluster.fork();
    });
} else {
    // Workers share the TCP connection on port 8000!
    http.createServer((req, res) => {
        res.writeHead(200);
        res.end(`Served by Worker PID: ${process.pid}
`);
    }).listen(8000);
    console.log(`Worker started with PID: ${process.pid}`);
}
19 & 20. Timers & Queues: Scheduling Precision & Microtask Ordering
📌 19.1 Timers: Drift & Drift Tolerance

In Node.js, setTimeout(fn, ms) does NOT guarantee execution at the exact millisecond requested. It guarantees only that the callback will execute no earlier than ms milliseconds, depending on whether the Call Stack is empty and other I/O operations have cleared.

🧠 20.1 The Master Microtask vs Macrotask Golden Ordering Rule
  1. Current Synchronous Call Stack (Finishes completely).
  2. process.nextTick() Queue (Drained completely before ANY microtask or macrotask).
  3. Promise Microtask Queue (Resolved promises, async/await continuations).
  4. Timers Phase (setTimeout, setInterval).
  5. Poll Phase (I/O callbacks).
  6. Check Phase (setImmediate).
  7. Close Callbacks (socket.on('close')).
💼 20.2 Sudheer J Style Interview Q&A Cards
Timers & Queues Senior / 9 LPA

Q: What is the exact difference between process.nextTick() and setImmediate()?

Key Answer: Despite their confusing names:
  • process.nextTick() runs immediately on the microtask queue as soon as the current operation finishes on the Call Stack, before the Event Loop continues to any other phase.
  • setImmediate() runs in the Check phase of the Event Loop, after the Timers and Poll (I/O) phases have completed.
In short: process.nextTick() fires before the next Event Loop phase; setImmediate() fires on the next check phase of the loop.
